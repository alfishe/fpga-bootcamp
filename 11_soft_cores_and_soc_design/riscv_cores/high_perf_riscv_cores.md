# High-Performance RISC-V Cores — Rocket, BOOM, CVA6 & XiangShan

Linux-capable, multi-issue, out-of-order RISC-V cores for large FPGAs and ASIC prototyping — from Berkeley's Rocket/BOOM to OpenHW's CVA6 and PKU's XiangShan. These cores target 64-bit address spaces, virtual memory, and operating system support, but their FPGA implementations carry significant resource costs.

---

## Core Comparison

| Core | ISA | Pipeline | Issue Width | LUTs (FPGA) | fmax (FPGA) | Linux | Language |
|---|---|---|---|---|---|---|---|
| **Rocket** | RV64IMAFDC | 5-stage, in-order | Single | ~15,000+ | 100+ MHz | Yes | Chisel |
| **BOOM** | RV64IMAFDC | Out-of-order, 6–8 stages | 2–4 wide | ~30,000+ | 50+ MHz | Yes | Chisel |
| **CVA6 (Ariane)** | RV64IMAFDC | 6-stage, in-order | Single | ~25,000+ | 50+ MHz | Yes | SystemVerilog |
| **XiangShan** | RV64IMAFDC | Out-of-order, 10+ stages | 6-wide | ~100,000+ | — (ASIC) | Yes | Chisel |

## Per-Core Architecture

### Rocket Chip — The Practical Linux Option

Rocket is a 5-stage in-order RV64GC core generated by the Rocket Chip SoC framework. It is the most practical Linux-capable RISC-V core for FPGA.

```
Rocket Core Pipeline
┌─────┐ ┌──────┐ ┌───────┐ ┌──────┐ ┌─────┐
│ IF  │→│ ID   │→│ EX    │→│ MEM  │→│ WB  │
│Fetch│ │Decode│ │Execute│ │Memory│ │Write│
└─────┘ └──────┘ └───────┘ └──────┘ └─────┘
          │                   │
     RoCC Accel ←→ TileLink Interconnect
```

| Feature | Detail |
|---|---|
| **Pipeline** | 5-stage in-order, single-issue |
| **Caches** | Configurable L1 I$, L1 D$; optional L2 via TileLink |
| **MMU** | Sv39 page table walker (Linux-compatible) |
| **FPU** | HardFPU (F/D extensions, IEEE 754 compliant) |
| **Debug** | RISC-V debug spec v0.13, JTAG |
| **RoCC** | Rocket Custom Coprocessor — tightly-coupled accelerator port |
| **Performance** | ~1.7 DMIPS/MHz, ~2.9 CoreMark/MHz |

**FPGA resource breakdown (Artix-7, single core, 16 KB I$/D$):**

| Component | LUTs | BRAM | DSP |
|---|---|---|---|
| Rocket core (no FPU) | ~8,000 | 8 | 0 |
| + FPU (F/D) | ~3,500 | 2 | 8 |
| + L2 cache (64 KB) | ~3,000 | 16 | 0 |
| + TileLink interconnect | ~500 | 0 | 0 |
| **Total (full SoC)** | ~15,000 | 26 | 8 |

### BOOM — Berkeley Out-of-Order Machine

BOOM is a superscalar out-of-order core built on the Rocket Chip framework. It shares the same TileLink interconnect and RoCC interface as Rocket but implements aggressive speculation.

```
BOOM Core Pipeline (simplified)
┌─────┐ ┌─────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
│Fetch│→│Decode│→│Rename│→│Issue │→│Read │→│Execute│→│Write │→│Commit│
│     │ │     │ │      │ │Queue │ │Reg  │ │ALU/FPU│ │Back  │ │      │
└─────┘ └─────┘ └──────┘ └──────┘ └──────┘ └──────┘ └──────┘ └──────┘
```

| Feature | Detail |
|---|---|
| **Pipeline** | 6–8 stages, out-of-order |
| **Issue Width** | 2–4 (configurable: SmallBoom → LargeBoom) |
| **Branch Prediction** | GShare + BTB + RAS |
| **Reorder Buffer** | 32–64 entries |
| **L1 Caches** | 16–64 KB I$, 16–64 KB D$ |
| **Performance** | ~3.5 CoreMark/MHz (LargeBoom, 4-wide) |

**BOOM configurations:**

| Config | Issue Width | ROB Size | L1 Caches | Target |
|---|---|---|---|---|
| **SmallBoom** | 2-wide | 32 | 16 KB I/D | Smallest OoO, still large for FPGA |
| **MediumBoom** | 3-wide | 48 | 32 KB I/D | Research balanced |
| **LargeBoom** | 4-wide | 64 | 64 KB I/D | Maximum performance, needs Kintex-7 325T+ |

> [!WARNING]
> BOOM on FPGA achieves only 30–50 MHz and consumes 30,000+ LUTs. It is primarily useful for **architecture research** and **ASIC prototyping**, not for production FPGA designs.

### CVA6 (Ariane) — The Readable RTL Option

CVA6 is a 6-stage in-order RV64GC core written in SystemVerilog. Originally developed at ETH Zürich as "Ariane," it is now maintained by the OpenHW Group.

```
CVA6 Pipeline
┌───────┐ ┌───────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
│ Fetch │→│ Issue │→│ EX 1 │→│ EX 2 │→│ MEM  │→│ WB   │
│       │ │       │ │  ALU │ │  FPU │ │      │ │      │
└───────┘ └───────┘ └──────┘ └──────┘ └──────┘ └──────┘
```

| Feature | Detail |
|---|---|
| **Pipeline** | 6-stage, in-order, single-issue |
| **Caches** | Configurable L1 I$ and D$ (16–64 KB) |
| **MMU** | Sv39 (Linux-compatible) |
| **FPU** | F/D extensions via separate FPU pipeline stage |
| **Debug** | RISC-V debug spec v0.13, JTAG |
| **Performance** | ~2.1 CoreMark/MHz |

**Key advantage:** CVA6 is written in **readable SystemVerilog** — no Chisel dependency. This makes it the best choice for teams that want to understand and modify the RTL directly, without learning Scala/Chisel.

**FPGA resource (Xilinx Kintex-7):** ~25,000 LUTs, ~40 BRAM, 8 DSP (with FPU). Fits on Kintex-7 325T or larger.

---

### XiangShan — The ASIC Research Core

XiangShan is a high-performance out-of-order RISC-V core developed at Peking University, targeting ASIC implementation at 2–4 GHz.

| Feature | Detail |
|---|---|
| **Pipeline** | 10+ stages, 6-wide out-of-order |
| **Target** | ASIC only — 7nm or 14nm process |
| **FPGA Prototype** | Possible on multi-FPGA systems (4× VCU118) at ~10 MHz |
| **Performance** | Targets SPEC CPU2006 20+ IPC (ASIC) |
| **Language** | Chisel |

**XiangShan is not practical for single-FPGA deployment.** It exists in this list for completeness — it represents the frontier of open-source high-performance RISC-V, but requires multi-million-gate ASIC processes to realize its design goals.

## Interconnect: TileLink vs AXI

Rocket Chip and BOOM use **TileLink** as their on-chip interconnect protocol. CVA6 uses **AXI4**. This has practical implications:

| Aspect | TileLink (Rocket/BOOM) | AXI4 (CVA6) |
|---|---|---|
| **Origin** | Berkeley (custom for RISC-V) | ARM (industry standard) |
| **Coherence** | Built-in (TileLink-UH/TL-C) | Requires ACE extension |
| **FPGA IP compatibility** | Limited — needs TileLink↔AXI bridge | Direct — most FPGA IP speaks AXI |
| **Tool support** | Chisel-only generators | Universal (Verilog/VHDL/Chisel) |
| **Debugging** | Custom protocol analyzers needed | Standard AXI protocol checkers |

> [!NOTE]
> Chipyard provides TileLink↔AXI bridge generators. If you need to connect Rocket to AXI peripherals (DDR controllers, PCIe blocks), the bridge adds ~200–500 LUTs and 1–2 cycles of latency.

## FPGA Reality Check

All four cores were **designed for ASIC**, not FPGA. This means:

| ASIC Design Assumption | FPGA Consequence |
|---|---|
| Target fmax: 1–2 GHz | FPGA achieves 30–100 MHz |
| SRAM cells for caches | BRAM blocks (4–16× larger area per bit) |
| Custom SRAM timing | BRAM fixed 1-cycle read latency |
| Wide issue, deep pipelines | Excessive LUT consumption for issue/ROB logic |
| High pin-count flip-flops | FPGA FFs are abundant but routing-limited |

### Practical Guidance

| Scenario | Best Choice |
|---|---|
| Need Linux on FPGA | **VexRiscv (Linux variant)** — 2,900 LUTs vs Rocket's 15,000+ |
| Need 64-bit Linux on FPGA | **Rocket** — smallest 64-bit Linux option |
| Need high-perf FPGA compute | **Hard ARM core (Zynq/Cyclone V SoC)** — 1 GHz+ vs 50–100 MHz soft core |
| Need ASIC prototyping | **Rocket or CVA6** — on VCU118 or similar large board |
| Need OoO architecture research | **BOOM** — but expect 30–50 MHz on FPGA |
| Need readable RTL for modification | **CVA6** — SystemVerilog, no Chisel |

## When to Use / When NOT to Use

### When to Use

- **ASIC prototyping** — Validate 64-bit RISC-V designs on FPGA before tape-out
- **Architecture research** — Study OoO execution, cache hierarchies, branch prediction
- **Chipyard ecosystem** — You want to use RoCC accelerators or Diplomacy-based SoC generation
- **64-bit Linux requirement** — You specifically need RV64 (not RV32 like VexRiscv)

### When NOT to Use

- **Production FPGA systems** — These cores are too large and too slow for real FPGA products; use VexRiscv or hard ARM cores
- **Resource-constrained designs** — 15K–100K LUTs for a single CPU core leaves no room for your actual application logic
- **Teams unfamiliar with Chisel** — Rocket and BOOM require Chisel expertise; CVA6 (SystemVerilog) is more accessible
- **When timing matters** — 50–100 MHz soft cores cannot compete with 1 GHz hard ARM cores

---

## Best Practices

1. **Use VexRiscv for Linux on FPGA** — Unless you specifically need RV64, VexRiscv's Linux variant is 5× smaller and 2× faster
2. **Start with Rocket, not BOOM** — Rocket is smaller, faster on FPGA, and more stable; only move to BOOM when you need OoO performance
3. **Use Chipyard for SoC generation** — Don't hand-wire TileLink interconnects; let Diplomacy handle parameter negotiation
4. **Budget 2× the expected LUTs** — Cache and interconnect overhead adds significantly to the core-only numbers
5. **Test on the largest FPGA first** — Start with Kintex-7 325T or VCU118; downscale only after verifying the design fits

## Antipatterns

| Antipattern | Why It Fails | Correct Approach |
|---|---|---|
| **Deploying BOOM in a production FPGA product** | 30 MHz fmax, 30K+ LUTs — no cost justification | Use Rocket for 64-bit or VexRiscv for 32-bit |
| **Ignoring BRAM-to-SRAM mapping overhead** | ASIC SRAM → FPGA BRAM costs 4–16× area; cache sizes that fit in ASIC may overflow BRAM | Reduce cache sizes for FPGA targets |
| **Mixing TileLink and AXI without bridges** | Protocol mismatch causes data corruption, not just errors | Use Chipyard's TL-to-AXI bridge generators |
| **Expecting ASIC-like fmax on FPGA** | FPGA routing adds 5–10 ns per stage; 10-stage pipeline at 2 GHz ASIC = 50 MHz on FPGA | Budget 50–100 MHz for FPGA prototyping |

## Pitfalls

### 1. Chisel Build Toolchain Complexity

Rocket and BOOM require **Java, SBT, and Chisel** — the same toolchain as VexRiscv but significantly heavier:

- First build: 10–30 minutes (downloads + compilation)
- Incremental build: 2–5 minutes
- Generated Verilog: 50K–200K lines (hard to read, not for manual editing)

### 2. Cache Parameter Mismatch

Rocket's L1 cache line size defaults to 64 bytes. If your memory subsystem (e.g., LiteDRAM) uses a different burst size, you need a TileLink adapter. This is not automatically detected — simulation will show mysterious cache miss behavior.

### 3. FPGA BRAM Fragmentation

Rocket's cache parameters (sets × ways × line size) may not map efficiently to FPGA BRAM blocks. For example, a 32 KB 4-way set-associative cache with 64-byte lines requires BRAM configurations that waste 20–30% of BRAM capacity.
