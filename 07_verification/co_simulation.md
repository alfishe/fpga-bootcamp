# Co-Simulation — Mixing Languages & External Models

Co-simulation connects your HDL design to code running in a different language or runtime. This lets you verify against C/C++ reference models, integrate MATLAB algorithms, boot real ARM Linux on an SoC design, or mix VHDL legacy IP with modern SV testbenches.

---

## DPI-C: Verilog ↔ C/C++

The Direct Programming Interface is the standard bridge between SystemVerilog and C/C++. It's zero-overhead — function calls cross the language boundary directly.

### Export (C called from SV)

```c
// reference_model.c
#include "svdpi.h"
int fir_filter(int input, int* coeffs) {
    int result = 0;
    for (int i = 0; i < 16; i++) result += input * coeffs[i];
    return result;
}
```

```systemverilog
// testbench.sv
import "DPI-C" function int fir_filter(input int data, input int coeffs[]);

always @(posedge clk) begin
    filtered <= fir_filter(raw_sample, tap_coeffs);
end
```

### Import (SV called from C)

```systemverilog
export "DPI-C" function sv_log;  // make visible to C

function void sv_log(int level, string msg);
    $display("[SV:%0d] %s", level, msg);
endfunction
```

| Direction | Keyword | Use |
|---|---|---|
| C → SV | `import "DPI-C"` | Call C functions from SV |
| SV → C | `export "DPI-C"` | Call SV functions from C |
| Types | `svdpi.h` | `svLogic`, `svBitVecVal`, arrays |
| Arrays | Open or sized | `[]` = open, `[15:0]` = sized |

## MATLAB / Simulink Co-Simulation

Two approaches for integrating MATLAB models:

| Method | How | Best For |
|---|---|---|
| **HDL Verifier** | Simulink ↔ HDL simulator via TCP/IP | Algorithm validation, DSP pipelines |
| **Export C via MATLAB Coder** | MATLAB → C → DPI-C → SV | Cheaper (no toolbox), good for fixed-point filters |
| **File I/O bridge** | $readmemh / $fwrite intermediate data | Quick-and-dirty; ~0 MB/s throughput |

## QEMU + SystemC for SoC Verification

For FPGA SoC designs (Zynq, Cyclone V SoC, MPSoC), verify HW/SW interaction before silicon:

```
┌──────────────────────────────────────┐
│  QEMU (ARM Linux + application code) │
│  ← socket / shared memory →         │
│  ┌──────────────────────────────┐    │
│  │  SystemC TLM-2.0 wrapper      │    │
│  │  ↔ AXI/AVMM transactions      │    │
│  │  ┌──────────────────────┐    │    │
│  │  │  HDL Simulator (RTL)   │    │    │
│  │  └──────────────────────┘    │    │
│  └──────────────────────────────┘    │
└──────────────────────────────────────┘
```

The CPU side runs real Linux + driver code; the FPGA side runs RTL. They communicate through a SystemC Transaction-Level Model (TLM) that translates AXI bursts into memory reads/writes visible to both sides.

## VHDL + SystemVerilog Mixing

| Scenario | Approach |
|---|---|
| VHDL DUT, SV testbench | Vivado/Questa natively support mixed-language elaboration |
| SV DUT, VHDL testbench | Supported but rarer; limit to simple wrappers |
| VHDL `foreign` attribute | Like DPI-C but VHDL-side; implementation-specific |
| Shared packages | Not possible — use C structs in DPI-C as intermediary |

## Verilator + C++ Testbenches

Verilator compiles Verilog to C++ and is increasingly popular for fast simulation:

```cpp
// top_test.cpp — Verilator C++ testbench
#include "Vtop.h"          // Generated by verilator
#include "verilated.h"

int main(int argc, char** argv) {
    Verilated::commandArgs(argc, argv);
    Vtop* top = new Vtop;
    
    // Reset sequence
    top->rst = 1;
    for (int i = 0; i < 10; i++) { top->clk = 0; top->eval(); top->clk = 1; top->eval(); }
    top->rst = 0;
    
    // Stimulus
    for (int cycle = 0; cycle < 1000; cycle++) {
        top->clk = 0; top->eval();
        top->clk = 1; top->eval();
        if (top->valid_out && top->data_out != expected[cycle]) {
            printf("MISMATCH at cycle %d: got %d, expected %d\n", cycle, top->data_out, expected[cycle]);
        }
    }
    
    top->final();
    delete top;
    return 0;
}
```

```bash
# Build and run
verilator --cc top.v --exe top_test.cpp --build
./obj_dir/Vtop
```

| Metric | Verilator + C++ | Icarus Verilog | Vivado xsim |
|---|---|---|---|
| **Speed** | 10–100× real-time | 0.1–1× real-time | 0.01–0.1× real-time |
| **Language support** | Verilog, limited SV | Verilog, limited SV | Full Verilog + VHDL + SV |
| **Waveform output** | VCD (via $dumpfile) | VCD | WDB (Vivado) |
| **Best for** | Long regression, CI/CD | Quick checks | Timing-accurate sim |

## cocotb Integration

cocotb (Coroutine-based Cosimulation TestBench) lets you write testbenches in Python while simulating in any backend:

```python
# test_fifo.py — cocotb testbench
import cocotb
from cocotb.clock import Clock
from cocotb.triggers import RisingEdge, Timer

@cocotb.test()
async def test_fifo_basic(dut):
    """Push 8 items, pop 8 items, verify order"""
    cocotb.start_soon(Clock(dut.clk, 10, units='ns').start())
    
    # Reset
    dut.rst.value = 1
    await RisingEdge(dut.clk)
    await RisingEdge(dut.clk)
    dut.rst.value = 0
    
    # Push
    for i in range(8):
        dut.wr_en.value = 1
        dut.din.value = i
        await RisingEdge(dut.clk)
    dut.wr_en.value = 0
    
    # Pop
    for i in range(8):
        dut.rd_en.value = 1
        await RisingEdge(dut.clk)
        assert dut.dout.value == i, f"Expected {i}, got {dut.dout.value}"
    dut.rd_en.value = 0
```

```bash
# Run with Verilator
MODULE=test_fifo TOPLEVEL=Vtop VERILATOR=/usr/bin/verilator make -C $(cocotb-config --makefiles)/Makefile.sim

# Run with Icarus
gtkwave wave.vcd &
```

## SystemC Transaction-Level Modeling (TLM)

SystemC TLM-2.0 enables fast functional simulation before RTL is ready:

| Abstraction Level | Speed vs RTL | Accuracy | Use Case |
|---|---|---|---|
| **Untimed TLM (LT)** | 1000–10000× faster | No timing | Architecture exploration |
| **Loosely Timed (LT)** | 100–1000× faster | Approximate timing | Software development |
| **Approximately Timed (AT)** | 10–100× faster | Cycle-approximate | Performance validation |
| **RTL (cycle-accurate)** | 1× (baseline) | Exact | Sign-off simulation |

### Typical TLM-2.0 SoC Flow
```
1. Build TLM model of CPU + peripherals (C++)
2. Develop and test firmware on TLM simulator (100× faster than RTL)
3. Replace TLM peripherals with RTL one-by-one (co-simulation)
4. Full RTL sign-off simulation
```

## DPI-C Performance Tips

| Pattern | Throughput | Recommendation |
|---|---|---|
| Per-sample function call | ~1M calls/s (overhead limited) | Good for control, bad for streaming |
| Batch transfer via array pointer | ~1 GB/s | Best for DSP pipelines |
| Shared memory (mmap) | ~10 GB/s | Best for video/frame-level data |
| VPI/ VHPI callback | ~100K calls/s | Slowest; use only for event triggers |

### Batch Transfer Pattern
```c
// Process 1024 samples per DPI call instead of 1
void process_batch(const int* input, int* output, int length) {
    for (int i = 0; i < length; i++) {
        output[i] = fir_reference(input[i]);
    }
}
```

```systemverilog
import "DPI-C" function void process_batch(input int in[], output int out[], input int length);

// Called once per 1024-sample block
always_ff @(posedge clk) begin
    if (block_ready) process_block(samples, results, 1024);
end
```

## Practical Co-Simulation Decision Table

| Your Situation | Approach |
|---|---|
| Reference model in C/C++ | DPI-C (fastest, standard) |
| DSP algorithm in MATLAB | MATLAB Coder → C → DPI-C |
| SoC: ARM Linux + FPGA | QEMU + SystemC + HDL simulator |
| Legacy VHDL IP + new SV | Mixed-language in Questa/Vivado |
| Third-party IP binary model | Vendor-specific encrypted model + SWIFT/VHPI |
| Fast regression tests | Verilator + C++ or cocotb + Verilator |
| Firmware development before RTL | SystemC TLM-2.0 (loosely timed) |
| Python-savvy team | cocotb + any simulator backend |

## Best Practices

1. **DPI-C over file I/O** — direct function calls are ~1000× faster than writing/reading $fwrite/$fread files. Don't use file I/O bridging for anything beyond one-off debug.
2. **QEMU co-simulation saves months** — catching a Linux driver bug before tape-out is worth the setup effort. The alternative is finding it on real silicon.
3. **Keep the C reference model simple** — if it's too complex to re-derive from the RTL spec, it's easy to introduce errors in the model that mask RTL bugs.
4. **Use batch DPI-C calls for streaming data** — per-sample calls have 100× more overhead than batch transfers.
5. **Verilator for CI, vendor simulator for sign-off** — Verilator is 100× faster but doesn't model timing; use it for functional regression, vendor tools for timing closure.
6. **cocotb for Python teams** — easier learning curve than SystemVerilog UVM for teams with Python expertise.

## Pitfall: DPI-C Array Overhead

Passing large arrays across DPI-C can become a bottleneck. Each call copies array data between SV and C memory spaces. For high-bandwidth data paths (>100 MB/s), consider streaming through a shared memory buffer or DMA model instead.
